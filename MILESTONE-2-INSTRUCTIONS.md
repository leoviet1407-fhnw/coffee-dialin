## 1. Ground rules for the implementation

- **Copy the structure of the course reference** `DevidMontecchiari/Station-bar-api` → `solution/`. The lecturer will recognise it, and the coaching asks us to explain the layers. Same files, same responsibilities:

  | Layer | File | Responsibility | Station Bar equivalent |
  |---|---|---|---|
  | HTTP interface | `api.py` | routes, status codes, `Location` header, error mapping | `bar_api/api.py` |
  | Input/output shapes | `models.py` | Pydantic schemas, input range validation (R1) | `bar_api/models.py` |
  | Application logic | `service.py` | business rules R2, R5–R8; **no FastAPI imports** | `bar_api/service.py` |
  | Pure rules | `advice.py` | ratio, time/ratio status, advice (R3–R4); pure functions | — (ours) |
  | Data access | `storage.py` | `JsonStore`: `seed.json` → `data.json`, atomic save via `.tmp` + replace, `RLock` | `bar_api/storage.py` |
  | Wiring | `main.py` | `create_app(data_file)`; data file from env var `COFFEE_DATA_FILE` | `main.py` |

- **Dependency injection exactly like the reference:** `create_app()` builds `JsonStore` → `CoffeeService`, stores it in `app.state.service`; a provider `get_service(request)` returns it; handlers take `service: Service` where `Service = Annotated[CoffeeService, Depends(get_service)]`.
- **One error shape everywhere:** `{"code": "...", "message": "..."}` with `invalid_input` → 422, `not_found` → 404, `conflict` → 409. Install the same three exception handlers as the reference (business error, `RequestValidationError`, `HTTPException`), so even malformed JSON and `/coffees/abc` return this shape. The service raises `CoffeeError(code, message)`.
- **422 vs 409 as taught (deck 05, slide 45):** wrong input = 422 (schema or rule about the input); valid input but conflicting state = 409 (e.g. not enough coffee left).
- **A failed request must not change `data.json`** (tests compare the file bytes before/after, like the reference).
- Server assigns `id` and derived fields; input models use `extra="forbid"` so clients cannot send `id`, `grams_left`, `ratio`, etc.
- Each route gets `operation_id`, `tags`, `response_model` and `responses={...}` with the `Error` model, so the generated contract documents the errors.
- Keep code small and readable. Short docstrings on each module saying which layer it is. Both of us must be able to explain every line in coaching.

### Models (`models.py`)

Base class `InputModel(BaseModel)` with `model_config = ConfigDict(extra="forbid")`.

- `Product`: `id: str, name, origin, roast_level, bag_size_g: int, shop_url: str`
- `CoffeeInput`: `product_id: str | None = None`, `name: str | None = Field(None, min_length=1)`, `origin: str | None`, `roast_level: str | None`, `roast_date: date`, `bag_size_g: int | None = Field(None, ge=50, le=5000)`
  - If `product_id` is given, the service fills missing `name/origin/roast_level/bag_size_g` from the product (unknown product → 422 `invalid_input`).
  - Without product: `name` and `bag_size_g` are required → 422.
- `CoffeeUpdate` (PUT, full replacement of editable fields): same as `CoffeeInput` plus `grams_left: float = Field(ge=0)`.
- `Coffee` (response): stored fields + `id`, `grams_left`, and **derived** `low_stock: bool`, `brews_left: int | None`, `days_off_roast: int`, `reorder_url: str | None` (product's `shop_url` only when `low_stock` and it is a PHIN product).
- Brew input as a **discriminated union** on `method` (gives a clean `oneOf` in OpenAPI):
  - `PhinBrewInput`: `method: Literal["phin"]`, `dose_g: float = Field(ge=10, le=25)`, `water_ml: int = Field(ge=60, le=200)`, `water_temp_c: int = Field(ge=85, le=100)`, `drip_time_s: int = Field(ge=60, le=600)`
  - `EspressoBrewInput`: `method: Literal["espresso"]`, `dose_g: float = Field(ge=5, le=30)`, `yield_g: float = Field(ge=5, le=120)`, `shot_time_s: int = Field(ge=5, le=120)`
  - both: `grind_setting: str | None = Field(None, max_length=20)`, `taste: Literal["sour", "balanced", "bitter"]` (required), `rating: int | None = Field(None, ge=1, le=5)`, `notes: str | None = Field(None, max_length=500)`
  - `BrewInput = Annotated[PhinBrewInput | EspressoBrewInput, Field(discriminator="method")]`
- `Advice`: `action: str`, `time_status: Literal["fast","ok","slow"]`, `ratio_status: Literal["low","ok","high"]`, `message: str`
- `Brew` (response): stored fields + `id`, `coffee_id`, `created_at`, derived `ratio: float` (1 decimal), `advice: Advice`, and `grams_left: float` (coffee stock after this brew).
- `Recipe`: `coffee_id`, `method`, `brew_id`, plus the brew's values for display.
- `Error`: `code: str, message: str`.

Add `model_config = {"json_schema_extra": {"examples": [...]}}` with one realistic example to `CoffeeInput`, `PhinBrewInput` and `EspressoBrewInput` (contract needs examples — D1).

## 5. Business rules (service + advice)

### `advice.py` — pure functions, no I/O

```python
def ratio(brew) -> float            # phin: water_ml / dose_g ; espresso: yield_g / dose_g ; round 1
def time_status(brew) -> str        # phin drip_time_s: <240 fast, >360 slow, else ok
                                    # espresso shot_time_s: <25 fast, >30 slow, else ok
def ratio_status(brew) -> str       # phin: <6 low, >8 high ; espresso: <1.8 low, >2.2 high ; else ok
def advise(brew) -> Advice
```

`advise` decision order (README "Brewing rules", R3–R4):

1. `taste == "balanced"` → `save_recipe` — *"Balanced. Save this brew as your recipe."* (taste beats numbers)
2. time `fast` → `grind_finer` — phin: *"Sour and fast (3:10). Grind finer or press the screen a little firmer."* / espresso: *"Fast shot (21 s). Grind finer."*
3. time `slow` → `grind_coarser` — phin: *"…Grind coarser or press more lightly."* / espresso: *"Slow shot (34 s). Grind coarser."*
4. time `ok` and `sour` → phin `hotter_water` (*"Try hotter water, up to 96 °C, or a little more coffee."*), espresso `longer_yield` (*"Increase the yield, e.g. 36 → 40 g."*)
5. time `ok` and `bitter` → phin `cooler_water` (*"Try cooler water, around 90 °C, or a little less coffee."*), espresso `shorter_yield` (*"Shorten the yield, e.g. 36 → 32 g."*)

Format times in messages as `m:ss` for phin and `NN s` for espresso. Messages start with taste + time, e.g. "Sour and fast (3:10).".

### `service.py` — `CoffeeService(store)`

Every write: `with self.store.lock:` → `data = load()` → check rules → change → `save(data)` → return. Raise before changing anything.

| Rule | Where | Behaviour |
|---|---|---|
| R1 ranges | `models.py` | Pydantic → 422 |
| R2 roast date not in future | `create_coffee`, `replace_coffee` | 422 `invalid_input` "roast_date cannot be in the future." |
| R3/R4 | `advice.py`, attached when a brew is returned (computed, not stored) | — |
| R5 recipe | `save_recipe` (step E) | brew must exist (404), belong to this coffee and method and be `balanced` → else 422; replaces existing recipe for that method |
| R6 stock | `log_brew` | `dose_g > grams_left` → **409 `conflict`** "Only 6 g left. Add a new bag first." Nothing saved. Else save the brew and subtract the dose: `grams_left = round(grams_left - dose_g, 1)` (`grams_left` is a float with one decimal) |
| R7 low stock | `coffee_view` (derived) | last dose = dose of the newest brew of that coffee, default 18. `low_stock = grams_left < 3 * last_dose`; `brews_left = floor(grams_left / last_dose)` |
| R8 deletes | `delete_brew`, `delete_coffee` | deleting a brew adds its dose back (and removes a recipe pointing to it); deleting a coffee removes its brews and recipes. 204 |
| not found | everywhere | 404 `not_found` "Coffee 999 was not found." |

`created_at` = `datetime.now(timezone.utc)` as ISO string. IDs never reused (counters in the file, like the reference).

## 6. HTTP interface (`api.py`)

| Method | Path | operation_id | Success | Declared errors |
|---|---|---|---|---|
| GET | `/api/products` | listProducts | 200 | — |
| GET | `/api/coffees` | listCoffees | 200 | — |
| POST | `/api/coffees` | createCoffee | 201 + `Location: /api/coffees/{id}` | 422 |
| GET | `/api/coffees/{coffee_id}` | readCoffee | 200 | 404, 422 |
| PUT | `/api/coffees/{coffee_id}` | replaceCoffee | 200 | 404, 422 |
| DELETE | `/api/coffees/{coffee_id}` | deleteCoffee | 204 | 404, 422 |
| GET | `/api/coffees/{coffee_id}/brews` | listBrews (`method` query optional: `phin`/`espresso`) | 200 | 404, 422 |
| POST | `/api/coffees/{coffee_id}/brews` | logBrew | 201 + `Location: /api/brews/{id}` | 404, 409, 422 |
| DELETE | `/api/brews/{brew_id}` | deleteBrew | 204 | 404, 422 |
| GET | `/api/coffees/{coffee_id}/recipes` | listRecipes | 200 | 404 (step E) |
| PUT | `/api/coffees/{coffee_id}/recipes/{method}` | saveRecipe, body `{"brew_id": 12}` | 200 | 404, 422 (step E) |

Path IDs: `Annotated[int, Path(ge=1)]` like `RecordId` in the reference. `FastAPI(title="PHIN Dial-in API", version="0.2.0", description=...)`. Brews list newest first.
